Code-level cycle: NVRMUserClient::esc holds fGate across ordinary SURF_DIRTY. That path can wait on accelerator family lock. A pageoff holding family lock can wait on a pending surface. GPU completion must clear that pending surface using SURF_DIRTY|GPU_MARK on the SAME NVK client, so it waits behind fGate. The kernel bypass for GPU_MARK is too late: it is reached only after acquiring fGate. This is a concrete possible lock cycle consistent with the capture; exact kernel lock ownership was not sampled.

Fix: GPU completion pending/ready/probe escapes alone use one dedicated IOUserClient connection, with its own fGate. Ordinary dirty operations keep the existing rendering connection. GPU_MARK handling returns before accelerator family lock, so ready can pass independently. No kernel or EFI change, no removed fences, no suppressed counter and no change to publication ordering. One process-lifetime connection, opened once with NVAccel carrier then NVRM fallback, used only by WindowServer. On opening failure returnOFF to initial probe, preserving WS completion waits; never fall back to the shared client. Transport errors/short outputs returnOFF and increment diagnostic errors. Telemetry completion_channel ready/calls/errors verifies runtime adoption after reboot.

Rejected alternative: simply try-lock early dirty marking and delay Scheduled until full publication. Host tests passed but lock-sensitive publication consequences were not proven safe, so that prototype was removed from source. It is preserved only in builds/frame-path-audit/commit-try-prototype.txt. Current source keeps original blocking dirty operation, isolates readiness transport instead.

Also includes prior two fixes: lazy single dummy address query per snapshot; deferred retries yield serial surface remark queue between2ms attempts.
