# Аудит пути кадра и 0.4.7

Исправлены две подтверждённые проблемы в коде. Их влияние на реальный FPS пока не измерено.

1. `nvmtl_address_snapshot` выполнял до 32 одинаковых вызовов `vkGetBufferDeviceAddress` для одного dummy-буфера при каждом снимке привязок. Теперь адрес запрашивается один раз на снимок, только если он нужен. Нулевой адрес также запоминается внутри снимка. Между снимками адрес не кэшируется: время жизни и замена буферов остаются прежними.
2. `nvmtl_surface_remark_later` спал по 2 мс в общей последовательной очереди, до 49 раз. Занятая поверхность задерживала готовые поверхности позади себя до 98 мс, а несколько таких задач суммировали задержку. Теперь повторная попытка планируется через `dispatch_after`; очередь свободна между попытками. Сохранены максимум 50 попыток, интервал 2 мс, удержание объекта, проверки seed до попытки и перед обновлением состояния, обработка отрицательного результата.

Проверка извлекает обе настоящие функции из исходников и компилирует с ASan/UBSan. Таблицы проверяются по всем 192 элементам, с пустыми/смешанными/полностью заполненными привязками и переходами между страницами. В модели очереди готовая поверхность публикуется в момент 0, пока первая остаётся занятой; также проверены 50 попыток, отмена по seed и отказ. Это доказательство устранения конкретных дефектов, а не замер input-to-photon.

Другие проверенные участки:

- `commitAndWaitUntilSubmitted` при активном kernel-wait ожидает отправку, а не полное завершение GPU. Удалять ожидание нельзя: оно упорядочивает передачу изображения дисплею.
- `waitUntilScheduled` также ожидает scheduled handlers. Это потенциальное дополнительное ожидание, но в текущих профилях нет доказательства, что именно обработчики создают основную задержку. Семантика не менялась.
- Основной worker вызывает `nvmtlAdvancePart` вне общего class-lock. Ahead-проход выполняется под общим lock и остаётся кандидатом на конкуренцию; снимать lock без переработки владения очередями небезопасно.
- Generic kernel pageoff игнорирует отрицательный результат `nvSurfWaitReady`; это существующая проблема корректности при таймауте. Direct present уже проверяет результат и удерживает прошлый кадр. Generic pageoff требует отдельного корректного протокола отказа; пропуск ожидания или копирование незавершённого изображения не являются оптимизацией.
- Фактическое копирование в память Intel занимает около 2,1 мс. В 0.4.4 промежуточная запись уже устранена. CPU-расход компоновки слоёв и записи команд остаётся распределённым между множеством функций.

Контроль 0.4.6: Safari ABBA дал 58,36/59,00 передачи в секунду OFF/ON, поэтому расширять предыдущий кэш ради FPS оснований нет. Нынешний аудит не объявляет найденные два дефекта единственной причиной всех задержек.

0.4.7 меняет только Metal plugin. EFI и ядро не меняются. Установщик сохраняет предыдущий пакет и настройки; проверяет именно установленный 0.4.6. После установки необходима ручная перезагрузка и проверка стекла. Для сбора использовать `kits/graphics-0.4.7/test-desktop.sh` с движением/изменением размера Safari. Кэш private images сохраняется в прежнем режиме, чтобы не смешивать эксперимент с его отключением.
