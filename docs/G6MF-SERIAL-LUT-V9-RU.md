# v9: последовательное заполнение LUT в WindowServer

Эксперимент для уже работающего v7/v8: LUT 1024, NVAccel 0.1.4,
NMIntelFB 0.1.4, Tahoe 25G241. Наблюдавшийся профиль показывает
CombineLUTs → CurrentHeadroom → mutex сразу на нескольких рабочих потоках.

Вместо изменения кэша headroom v9 меняет планирование одного заполнения LUT:
его исходный block выполняется последовательно, ровно по одному разу для
каждого индекса. Сохраняются вычисления RGB, ширина 1024 и обращения к
актуальному состоянию дисплея. Нет постоянной подмены headroom или изменения
его флагов. Возможный выигрыш — уменьшение конкуренции за mutex. Реальный
выигрыш и поведение при изменении яркости пока не проверены на Mac.

## Область действия

Загрузчик меняет указатель импорта dispatch_apply в памяти своего процесса
WindowServer. Требуются точный CoreDisplay UUID
24682CF5-C129-3A3F-91C7-80A228552372, проверенный call site, x86_64 stub и
оригинальный dispatch_apply в слоте. Указатель может быть общим для нескольких
импортов в shared cache: поэтому сам обработчик дополнительно проверяет адрес
возврата именно из LUT и адрес именно её block_invoke. Остальные вызовы
передаются оригинальному dispatch_apply с исходными аргументами.

Меняется только выровненный указатель данных, атомарно, с VM_PROT_COPY и
восстановлением прежней защиты страницы. Исполняемые страницы не меняются.
Изменение локально процессу. Apple-файлы, EFI, kexts и Auxiliary KC не меняются.
Оригинальный NVIDIA-плагин остаётся в том же bundle. Сначала сохраняется весь
текущий bundle v7 и настройки; при ошибке проверки установщик восстанавливает их.

## Проверка в Tahoe

    sudo bash /Volumes/1401/NullMoth-G6MF-Bridge-v9-SerialLUT/install-serial.sh

Установщик проверяет codesign и отпечатки __text текущей обёртки/оригинального
плагина (подписи могут меняться при codesign), подписывает кандидат и запускает
два отдельных процесса. serial-probe загружает реальный CoreDisplay, проверяет
привязку импорта, последовательные 1024 итерации и передачу другого вызова
оригинальному libdispatch. lut-probe проверяет лимит 1024 и NVIDIA compute.
При отказе появляется причина в serial-probe.txt или lut-probe.txt; изменения
откатываются. Не перезагружаться после ошибки как будто установка завершилась.

Только после SERIAL LUT READY перезагрузиться. После входа повторить обычные
движения окон/анимации для прогрева, затем:

    sudo bash /Volumes/1401/NullMoth-G6MF-Bridge-v9-SerialLUT/profile-perf.sh

20 секунд двигать окно и дождаться PROFILE COLLECTION COMPLETE.
Проверить плавность, яркость, цвета/градиенты и Genie/Glass.
В графическом логе нужны обе записи G6MF-LUT-SERIAL: import installed и
matched real CoreDisplay LUT. Успех отдельного probe не доказывает, что
реальный WindowServer дошёл до распознанного вызова, или что FPS вырос.

По возможности полезно сделать второй такой профиль в том же сеансе для
проверки повторяемости. Новый способ CPU-копирования v8 при загрузке остаётся
в режиме 0: в этом тесте исследуется только планирование LUT.

## Контроль и откат

Отключить перехват для следующей загрузки, сохранив v7 LUT 1024:

    sudo bash /Volumes/1401/NullMoth-G6MF-Bridge-v9-SerialLUT/set-serial-lut.sh 0

Перезагрузиться и повторить профиль с теми же движениями. Для включения —
значение 1 и ещё одна перезагрузка. Файл читается при загрузке обёртки;
изменение файла не перепривязывает импорт в уже работающем WindowServer.

Полностью восстановить сохранённый bundle и настройки:

    sudo bash /Volumes/1401/NullMoth-G6MF-Bridge-v9-SerialLUT/rollback-lut.sh ПУТЬ_ИЗ_last-lut-backup.txt

В Recovery вторым аргументом можно указать корень Data-тома, а путь бэкапа
указывается так, как он виден там. После восстановления перезагрузиться.
Автосбор следующей загрузки установлен на случай отсутствия рабочего стола:
подождать пять минут и вернуться в Linux для разбора отчёта.

## Проверки до аппаратного теста

CPU/ASan/UBSan: точные индексы и порядок, выбор единственного call site и
block, передача других вызовов оригиналу; отказ по процессу, конфигу, UUID,
инструкциям и защите VM; восстановление указателя при отказе восстановления
защиты страницы. Настоящие Bash installer/rollback проверены с mock Darwin:
успех и ошибки codesign, обоих probes, маркеров и установки автосбора.
Mach-O продукты собираются из C в Linux/CI, Xcode на целевом Mac не нужен.
Это ещё не аппаратное подтверждение устранения рывков.

Открытая реализация Apple libdispatch использована для сверки последовательного
пути dispatch_apply: https://github.com/apple-oss-distributions/libdispatch/blob/main/src/apply.c
