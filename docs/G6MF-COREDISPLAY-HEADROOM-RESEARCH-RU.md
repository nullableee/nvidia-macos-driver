# Исследование оставшихся ожиданий LUT после v8

Разбор точного CoreDisplay 291.4, UUID
24682CF5-C129-3A3F-91C7-80A228552372, из Tahoe 25G241.
Использованы ранее извлечённый бинарник и последние синхронные sample;
новое монтирование APFS и новый запуск macOS не требовались.
Apple-бинарники и дизассемблирование остаются вне репозитория.

## Что удалось уточнить

RunFullDisplayPipe заполняет LUT через dispatch_apply. Его block_invoke
вызывает CombineLUTs отдельно для RGB. Внутри CombineLUTs запрашивается
CurrentHeadroom; в измеренном профиле виден путь через mutex дисплея.
При ширине 1024 это до 3072 таких запросов на одно заполнение таблицы.
Это статическая кратность цикла, не измеренное число заполнений в секунду.
Профиль показывает заполнение во время теста, но не доказывает, что LUT
строится заново для абсолютно каждого показанного кадра.

У CurrentHeadroom есть два различных ранних пути:

- состояние по смещениям +0x45c / +0x460;
- кэш результата по +0x220 / +0x224.

Уточнение к прежнему описанию: первый путь нельзя считать обычным кэшем,
который достаточно прогреть. Прямые записи в эти поля найдены в
CoreDisplay_Display_SetShinyData_Server: при ненулевом указателе значение
копируется в +0x45c, флаг +0x460 устанавливается; при отсутствии значения
флаг сбрасывается. Это управляемое внешними данными состояние CoreDisplay.
Сам CurrentHeadroom не заполняет его как свой обычный кэш.

В альтернативной ветви CurrentHeadroom берёт mutex, проверяет внутренний
объект и может вернуть результат, не устанавливая обычный cache-valid флаг
+0x224. Поэтому повторные запросы могут продолжать брать mutex. Этот путь
согласуется со sample, но семантика внутренних объектов и необходимость
повторной проверки ещё не установлены. Называть это доказанным багом Apple
или неверными возможностями HDR драйвера преждевременно.

NMIntelFB сейчас возвращает успех из setGammaTable без программирования
аппаратной LUT, а AGDC публикует проверенные plane-scaler capabilities.
Поэтому добавление gamma capability без реализации таблицы не является
корректным способом убрать программную цветокоррекцию.

## Следствие для следующего изменения

Для устранения конкуренции важна кратность обращения к общему состоянию
дисплея при построении одной таблицы, а не дальнейшее ускорение записей
в Intel aperture. Возможный алгоритм — получить зависящие только от дисплея
параметры один раз на построение LUT и передать их вычислениям RGB.
Для текущего закрытого CoreDisplay это ещё не готовый патч: нужно установить
правила изменения/инвалидации этих параметров и выбрать место вмешательства.
Подмена ShinyData постоянным значением без этих правил может менять цветовую
семантику и не подготовлена для установки пользователю.

Текущий результат этапа — локализация и уточнение владельца состояния,
а не подтверждённое исправление рывков. Рабочие v7/v8 не заменялись;
новая версия драйвера по этому исследованию пока не выпущена.


## Продолжение: инвалидация и точное место возврата

В точном бинарнике найдены прямые обращения к cache-valid +0x224:
SetEDRScaleFactor сбрасывает его после изменения коэффициента +0x170;
PropertyChanged также сбрасывает его. Это подтверждает наличие штатной
инвалидации, но не доказывает полноту для предлагаемого расширения кэша.
SetEDRScaleFactor использует отдельный lock; пока не установлено, гарантирует
ли вызывающий код сериализацию с worker-потоками LUT. Нельзя считать запись
флага +0x224 безопасной только на основании совпадения последовательных кадров.

Locked-путь CurrentHeadroom сохраняет исходный результат в локальный слот,
вызывает unlock и восстанавливает результат. Найдена точная точка вызова
unlock: unslid 0x7ff805385cc3. Наличие этой точки позволяет сформулировать
кандидат: кэшировать вычисленный результат перед unlock, с отдельным условием
SDR, используя штатные сбросы. Это кандидат для дальнейшего анализа гонок,
а не разрешение записать cache-valid в действующий WindowServer.

Добавлен tools/g6mf_audit_headroom.py: воспроизводимый read-only аудит
извлечённого Mach-O, проверка UUID, символов, границ и соседних инструкций
точки возврата. Требуется capstone 5.x. Пример запуска:

    python tools/g6mf_audit_headroom.py /path/to/CoreDisplay --out /path/to/headroom-audit.json

Аудитор успешно прошёл на извлечённой 25G241 библиотеке. Его JSON и полный
дизассемблированный контекст остаются вне Git. Список обращений к смещениям
содержит кандидатов для data-flow review; сам по себе он не доказывает, что
произвольный базовый регистр всегда указывает на объект Display.

## Выбранный эксперимент v9

Вместо расширения кэша выбран вариант без записи в поля headroom: исходное
заполнение LUT выполняется последовательно. Подтверждено по indirect symbol
table извлечённого Mach-O: stub 0x7ff80543a230 импортирует _dispatch_apply.
Его указатель данных перепривязывается локально процессу; обработчик выбирает
только исходный LUT call site и исходный block_invoke. Все остальные вызовы
передаются оригиналу. Сохранены исходные вычисления и правила инвалидации.
Реальный shared-cache import slot может быть общим для нескольких библиотек,
поэтому обе проверки адресов обязательны. Ни кэш headroom, ни исполняемые
страницы не меняются. Установка импорта и эффект на плавность требуют Mac.
См. [комплект v9](G6MF-SERIAL-LUT-V9-RU.md).
