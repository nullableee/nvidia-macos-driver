# Первый аппаратный результат v7: LUT 1024

Источники: perf-20261030-100646-851, profile-20261030-100645-836,
lut-probe.txt. Скопированы с флешки локально в G6MF-Hardware-2026-10-29.
Сравнение с perf-20261030-003535-808 / profile-20261030-003534-795 (v6).
Это два ручных прогона, а не строго одинаковая автоматическая нагрузка.

Установочный probe прошёл: LUT CAP: 1024, blit/readback и два compute dispatch
с проверкой результатов и guard words. В реальном WindowServer[200] есть оба
сообщения G6MF-LUT: установлен override; original=16384, advertised=1024.
Таким образом, применение ограничения подтверждено не только тестовым процессом.
Пользователь подтвердил уменьшение лагов; рывки остались.

| Успешные копирования на панель за 20 с | 408 | 1247 |

Частота копирований выросла в 3.06 раза. Это не измерение уникальных кадров
приложения и не доказательство постоянных 62 FPS. VBL остаётся около 163 Гц;
60-герцовый предел таймера не обнаружен. Время ядрового обработчика почти
не изменилось: выигрыш согласуется с изменением пользовательского пути LUT.

Гистограмма интервалов v7 (<7, 7–12, 12–20, 20–28, 28–40, >=40 мс):
1, 319, 762, 127, 27, 14. Из 1250 интервалов 168 (13.44%) >=20 мс,
14 (1.12%) >=40 мс. В v6 402 из 407 интервалов были >=40 мс.
Неравномерность осталась: среднее 16.3 мс не означает равномерный вывод.
Максимумы в summary относятся ко всей загрузке, не только к этим 20 секундам.

Дельты: iop_fail=0, surface_gpu_timeouts=0, iop_empty=0, iop_copy_skip=2.
Два пропуска означают сохранение предыдущего изображения, пока новые пиксели
ещё не доступны в системной памяти; это не GPU timeout. Чтение счётчиков
последовательное, поэтому количества по стадиям могут немного отличаться.

В sample осталось CombineLUTs → CurrentHeadroom → mutex. Крупнейшая ветвь
главного потока RunFullDisplayPipe +15308 уменьшилась с 1117 до 221 samples
при почти одинаковом числе samples главного потока (1742 и 1738).
Collapsed mutexwait по всем потокам: 12675 → 2215; mutexdrop: 6656 → 988.
Это счётчики стеков, не проценты загрузки CPU.

Также Thread_3000 проводит 1433 из 1738 samples в
NVMTLDevice newRenderPipelineStateWithDescriptor:error: →
nvmtl_vk_pipeline_create_rt → nvmtl_vk_pipeline_create_impl;
ниже присутствует преобразование SPIR-V / buffer addresses.
Это асинхронная работа QuartzCore dispatch_async_pipeline. В старом профиле
таких стеков не найдено. Наличие работы подтверждено, но sample не показывает,
была ли это разовая компиляция новых вариантов или повторяющаяся потеря кэша.
По нему нельзя утверждать, что именно компиляция вызывает каждый рывок.

Сбор начался через 1 мин 47 с после запуска WindowServer. Следующий тест:
сохранить LUT 1024, после входа несколько минут пользоваться рабочим столом,
повторить те же движения/анимации, затем выполнить profile-perf.sh дважды
без перезагрузки. Сравнить частоту копий, хвост интервалов и стек компиляции.
Это отделит прогрев шейдеров от постоянной нагрузки LUT/композитинга.
Новых изменений EFI/kexts/плагина для этого теста не требуется.

v7 остаётся обходом с меньшей точностью цветовой таблицы и ограничением всех
запросов maxTextureWidth1D этого NVMTLDevice внутри WindowServer. Это ещё не
окончательное исправление CoreDisplay и не подтверждение плавности 165 FPS.

Повторные тесты без заметной компиляции дали 66.20 и 63.60 копирования/с;
см. [анализ повторных прогонов](G6MF-LUT-V7-WARM-RESULT-RU.md).
